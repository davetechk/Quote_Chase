### 2.2 Flows

#### a. Signup → profile creation → trial start
1. `auth/signup.html:131-190` `handleSignup()` validates 4 fields (business name, your name, email, password ≥ 8).
2. `js/auth.js:4-8` `signUp()` → `supabase.auth.signUp({ email, password })`.
3. If `authData.user.id` is missing, it shows "check your inbox" (`signup.html:154-159`). **Note:** with Supabase email confirmation ON, `signUp` still returns `user.id` but `session: null`. In that case the code continues to step 4 as an **unauthenticated** client, so the insert will likely fail under RLS. **UNCLEAR** whether confirmation is enabled in the project.
4. `signup.html:165-174` does a **client-side** `supabase.from('profiles').insert({ user_id, business_name, owner_name, plan:'free', subscription_status:'trial', trial_ends_at: now+14d (browser clock), quotes_used_this_month:0, quote_limit:0 })`. In the uncommitted working copy, `trade:'roofer'` has been removed; in production (HEAD) it is still present.
5. Redirects to `/auth/onboarding.html`.
6. The trial starts the moment that row exists. There is no server-side trial record, no DB trigger and no welcome email. If step 4 fails after step 2 succeeded, the auth user is orphaned with no profile. Every dashboard page then dies, because `getProfile()` uses `.single()`, which throws, and the page shows nothing (`js/dashboard.js:26-34`).

#### b. Login / logout / password reset
- **Login:** `auth/login.html:102-127` → `js/auth.js:11-15` `signInWithPassword` → `/dashboard/index.html`. Error strings are pattern-matched (`invalid login`, `email not confirmed`); anything else is shown raw.
- **Logout:** sidebar button (`js/dashboard.js:132,152`) → `js/auth.js:18-22` `supabase.auth.signOut()` → `/auth/login.html`.
- **Forgot:** `auth/forgot-password.html:74-91` → `js/auth.js:39-44` `resetPasswordForEmail(email, { redirectTo: origin + '/auth/reset-password.html' })`.
- **Reset:** `auth/reset-password.html:111-117` listens for `onAuthStateChange` → `PASSWORD_RECOVERY` and then shows the form. If no event arrives within 3 s (line 120-122), it shows "Link expired". The `SIGNED_IN && !session` branch (line 114) can never be true. `updatePassword` → `supabase.auth.updateUser({ password })`.
- Session storage is the supabase-js default (localStorage). The Supabase Auth email templates and sender are not in the repo (**UNCLEAR**).

   - Client-side quota check (line 235-240): only when `quote_limit > 0`.
   - `supabase.from('quotes').insert({ business_id: profile.id, customer_name, customer_email, customer_phone, job_description, quote_amount, status:'sent' }).select().single()` (line 246-258).
   - `supabase.from('profiles').update({ quotes_used_this_month: used + 1 }).eq('id', profile.id)` (line 263-266). The result is not checked.
   - `fetch(`${supabase.supabaseUrl}/functions/v1/send-message`, POST, Authorization: Bearer <user JWT>)` with body `{ type:'quote', quoteId, profile:{business_name, owner_name}, customer:{name,email,phone}, job, quoteAmount }` (line 272-296).

#### d. Scheduled follow-ups (day 2, 5, 10, 20)
- **Trigger:** **UNCLEAR.** `struc.txt:42-44` lists `supabase/functions/send-followups/{index.ts,config.toml}`, which suggests a scheduled function (pg_cron + `net.http_post` per the stack description), but neither the function nor the cron definition is in the repo.
- **Duplicate prevention:** the client reads boolean columns `followup_2_sent`, `followup_5_sent`, `followup_10_sent`, `followup_20_sent` (`dashboard/quotes.html:135-147, 234-247`; `admin/index.html:187`). These are presumably set by `send-followups` as idempotency flags. **UNCLEAR** whether the update is atomic (e.g. `UPDATE … WHERE followup_5_sent = false RETURNING`) or whether a cron overlap could double-send.
- **How they stop:** **UNCLEAR server-side.** The client signals it in two ways:
  - Won/Lost set `status` and `customer_replied = true` (`dashboard/index.html:137-148`, `dashboard/quotes.html:150-172`).
  - **"Replied" sets `status = 'followup'` only and does NOT set `customer_replied`** (`dashboard/index.html:169`, `quotes.html:191, 286`). If the server stops on `customer_replied` or `status in (won, lost)`, then marking a quote "Replied" does **not** stop the chasing, and `'followup'` is also the "Following Up" status label.

## 5. SMS (BIRD) — UK vs US

**The Bird integration code is not in this repository.** It lives in the `send-message` (and presumably `send-followups`) Edge Function, which has never been committed. So:

- **How UK vs US is chosen:** **UNCLEAR.** No country detection, channel selection or sender logic exists in client code.
- **Exact request payload / endpoint per region:** **UNCLEAR.** The client never calls Bird. For reference, Bird's Channels API is normally `POST https://api.bird.com/workspaces/{workspaceId}/channels/{channelId}/messages` with header `Authorization: AccessKey <key>` and body `{ "receiver": { "contacts": [{ "identifierValue": "+1XXXXXXXXXX", "identifierKey": "phonenumber" }] }, "body": { "type": "text", "text": { "text": "…" } } }`. Compare this with what `send-message` actually sends.
- **Env vars:** **UNCLEAR.** None are referenced client-side. Check in Supabase → Edge Functions → Secrets for names like `BIRD_ACCESS_KEY`, `BIRD_WORKSPACE_ID`, `BIRD_CHANNEL_ID_UK`, `BIRD_CHANNEL_ID_US` (or `BIRD_US_CHANNEL_ID`). A mismatch between the name the code reads and the name that is set produces `undefined` in the URL path, which gives a 404/400 from Bird.

### What the client code does to phone numbers (the only SMS-related code present)

`dashboard/new-quote.html:208-213`:
```js
function cleanPhone(raw) {
  if (!raw) return null;
  const digits = raw.replace(/\s+/g, '');      // only whitespace removed
  if (digits.startsWith('07')) return '+44' + digits.slice(1);
  return digits;
}
```

The result is stored in `quotes.customer_phone` and sent to `send-message` as `customer.phone`.

| US user types | Stored / sent value | E.164? |
|---|---|---|
| `+1 (415) 555-0123` | `+1(415)555-0123` | ✗ (parentheses, dash) |
| `(415) 555-0123` | `(415)555-0123` | ✗ (no country code) |
| `415-555-0123` | `415-555-0123` | ✗ |
| `4155550123` | `4155550123` | ✗ (no `+1`) |
| `1 415 555 0123` | `14155550123` | ✗ (no `+`) |
| `+14155550123` | `+14155550123` | ✓ (only this works) |

Other client-side context: the phone placeholder is `+44 7700 900000` (`new-quote.html:61`), the amount label is `(£)` (line 44), and every format function is `en-GB`/`£`. There is no country setting on `profiles`, so the server cannot know a business is US-based unless it infers it from the number.

### Plausible code-side causes of US failure, ranked

1. **Non-E.164 US numbers.** `cleanPhone` leaves punctuation in and never adds `+1`. If `send-message` routes on prefix (`startsWith('+1')` → US channel, else UK), most US numbers either fall to the UK channel or are rejected by Bird as an invalid identifier. Fix: normalise to E.164 with a real library (libphonenumber-js) using a per-business default country, and validate before insert.
2. **UK sender reused for US.** If the UK route uses an **alphanumeric sender ID** (e.g. "QuoteChase") and the US path reuses that channel/sender, US carriers reject it: US SMS must come from the approved 10DLC/toll-free number's channel. Check that the US branch uses the US channel ID, not the UK one.
3. **US channel env var missing or misnamed** in Edge Function secrets, or the US channel in a **different Bird workspace** that needs a different workspace ID/access key than the UK one.
4. **Routing defaults to UK.** Code like `phone.startsWith('+44') ? UK : US` or the inverse, with no `+1` check. Combined with cause 1, US numbers can hit the wrong branch.
5. **Message content filtered by US carriers.** Toll-free/10DLC traffic needs the registered brand name and opt-out language ("Reply STOP to opt out") matching the approved use-case sample. Links, especially non-branded or shortened ones, raise filtering. Bird may accept (2xx) and then the carrier drops the message, so check Bird delivery reports, not just the API response.
6. **Errors swallowed.** The client treats any 2xx from `send-message` as full success (`new-quote.html:298-299`). If the function catches the Bird error and still returns 200, failures are invisible. Make the function return a per-channel result (`{ email: 'sent', sms: 'failed: <reason>' }`) and log Bird's response body.
7. **Edge Function deployed from a stale copy.** Because the function isn't version-controlled, the deployed code may predate the US work entirely. Check with `supabase functions download send-message`.

## 11. SUMMARY

### Overview
1. QuoteChase is a 14-page static vanilla HTML/CSS/JS site (≈5,900 lines of tracked source) on Vercel, talking directly to Supabase with the anon key.
2. **No backend code is in the repo**: Edge Functions, schema, RLS, RPCs, cron and any Dodo webhook live only in Supabase, unversioned and unauditable.
3. Client flows (signup, login, reset, dashboard, quotes, settings, public quote page, admin) are coherent and consistently styled, with `sanitize()` used correctly on all `innerHTML` sinks.
4. Most "previous audit" fixes exist only as **uncommitted** changes, so production still has the dead "Send quote" button.
5. Authorisation is largely client-side: the paywall is an overlay, billing fields are written by the browser, the admin gate is a JS email check, and the public quote page needs open anon access to `quotes`.
6. Payment activation has no code in the repo; the path from Dodo checkout to an active subscription is unverified.
7. Follow-up stopping is semantically broken ("Replied" doesn't set `customer_replied`; "Lost" shows customers "already accepted"), and there is no reply detection despite the marketing claim.
8. SMS normalisation is UK-only (`07`→`+44`), which is the leading code-side explanation for US SMS failing. Currency and locale are GBP-only throughout.
9. There is zero PWA groundwork: no manifest, SW, square icons, theme-color, safe-area handling or pinned dependencies, and every page needs network.
10. Landing copy targets generic "service businesses/consultants", while the app, legal terms and defaults target trades. It still contains fabricated social proof and sells team features that don't exist.

### The 5 things that most need fixing before a January 2027 launch
1. **Commit the backend and lock down authorisation.**
   - Pull Supabase into `supabase/` (migrations + functions).
   - Admin-check the 3 admin RPCs.
   - Replace anon `quotes` access with token-based `get_public_quote`/`accept_quote` RPCs.
   - Make profile creation a DB trigger and revoke client writes to billing/usage columns (C2, C3, H1, H5, H6).
2. **Build and verify the Dodo webhook**, with signature verification, idempotency, and plan/limit mapping including cancel/renew/fail, plus server-side trial expiry and quota enforcement in `send-message` (C4, M2, M3).
3. **Ship the working send path and make it reliable.**
   - Commit and push the uncommitted fixes now (C1).
   - Move insert + send + usage into one Edge Function with per-channel delivery status.
   - Normalise phones to E.164 per country (H8, H9).
   - Fix US routing once the function source is in hand (§5).
4. **Fix follow-up correctness:** a real `replied` state that stops chasing, a correct public-page state for lost quotes, contractor notification on accept, and then inbound email (reply detection / BCC intake) so "stops when they reply" becomes true (H2, H3, H4, §6).
5. **Clean up trust and compliance before traffic:**
   - Rotate and redact the leaked credential and add `.gitignore`/`.vercelignore` (C5, M13).
   - Add GA consent or remove GA, and correct the privacy policy (H7).
   - Remove the fake social proof and unbuilt-feature claims (M7, M12).
   - Make account deletion real (H10).
   - Refocus the copy on roofers, builders and trades (§9).
